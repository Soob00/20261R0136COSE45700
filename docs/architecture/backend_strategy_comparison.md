# Backend Strategy Comparison

## 목적
이 문서는 현재 레포(Next.js 16 기반 Avatar Editor)에 대해 아래 2가지 백엔드 전략을 비교한다.

1. Java 백엔드(Spring 등)와 프론트 분리 연동
2. 이 레포 내부에 Next Route Handler 기반 백엔드 직접 구현(BFF/통합형)

## 현재 레포 전제
- 프론트는 이미 `src/lib/api/types.ts` 기반 API 추상화 계층을 보유
- 기본 구현은 `src/lib/api/local.ts` (localStorage)
- 3D 편집 상태/버전 관리 로직은 프론트에 이미 구조화되어 있음
- Python 파이프라인(`face-feature`) 및 자산 스크립트(`scripts`)는 별도 실행 축

## 요약 결론
- 단기(빠른 제품화/MVP): **레포 내부 백엔드 직접 구현**이 유리
- 중장기(조직 표준/대규모 운영): **Java 백엔드 분리**가 유리
- 현실적인 추천: **1차 통합형(Next 내부) → 필요 시 Java 분리**의 단계적 전환

## 상세 비교

### 1) 개발 속도
- Java 분리 연동
  - 장점: 백엔드 표준(보안/검증/관측) 재사용 가능
  - 단점: DTO/계약/CORS/인증/배포 파이프라인 협업 비용이 초기부터 발생
- Next 내부 구현
  - 장점: 같은 레포에서 타입 공유 및 빠른 반복 가능
  - 단점: 백엔드 복잡도 상승 시 프론트 레포 부담 증가

판정: 초기 속도는 Next 내부 구현 우세.

### 2) 아키텍처 일관성/경계
- Java 분리 연동
  - 장점: 도메인 경계 명확, 멀티 클라이언트(웹/앱) 재사용 용이
  - 단점: 프론트 입장에선 네트워크 경계가 즉시 생겨 개발 민첩성 저하
- Next 내부 구현
  - 장점: BFF 형태로 UI 요구사항 반영이 빠름
  - 단점: 도메인 로직이 비대해지면 관심사 분리가 약해질 수 있음

판정: 장기 경계는 Java 우세, UI 중심 반복은 Next 우세.

### 3) 운영/배포
- Java 분리 연동
  - 장점: 기존 Java 운영 스택(모니터링, 장애 대응, 롤백) 활용
  - 단점: 프론트+백엔드 2개 배포 단위 운영 필요
- Next 내부 구현
  - 장점: 단일 배포 단위로 단순화 가능
  - 단점: Node 런타임 운영 성숙도가 팀마다 다를 수 있음

판정: 운영 표준이 이미 Java에 있으면 Java 우세, 단순성은 Next 우세.

### 4) 성능/확장성
- Java 분리 연동
  - 장점: 고부하 API, 복잡 트랜잭션, 비동기 배치 확장에 유리
  - 단점: 초기엔 과설계가 될 수 있음
- Next 내부 구현
  - 장점: BFF/중소규모 API에 충분
  - 단점: 고부하/복잡 쿼리/장기 배치가 늘면 분리 필요성 증가

판정: 중대형 확장 계획이 명확하면 Java 우세.

### 5) 데이터/트랜잭션
- Java 분리 연동
  - 장점: JPA/MyBatis, 트랜잭션, 락, 정합성 정책에 강함
- Next 내부 구현
  - 장점: Prisma/SQL 직접 접근으로 단순 CRUD는 빠르게 가능
  - 단점: 복잡 도메인 정합성은 추가 설계 필요

판정: 복잡 도메인일수록 Java 우세.

### 6) 팀 협업 구조
- Java 분리 연동
  - 장점: 역할 분담 명확(프론트/백엔드)
  - 단점: 스펙 협의/동기화 비용 증가
- Next 내부 구현
  - 장점: 소규모 팀에서 end-to-end 속도 높음
  - 단점: 특정 인력에게 지식 집중 가능

판정: 소규모/풀스택 중심이면 Next 우세.

## 의사결정 체크리스트
아래 항목 중 `예`가 많을수록 해당 전략이 적합하다.

### Java 분리 연동이 맞는 경우
- 이미 Java 기반 공통 인증/권한/감사 체계가 있다.
- 다른 서비스(모바일/관리자/외부 파트너)도 같은 API를 재사용해야 한다.
- 복잡 트랜잭션/대규모 데이터 처리 요구가 확실하다.
- 백엔드 전담팀이 별도로 있고 운영 체계가 성숙하다.

### Next 내부 구현이 맞는 경우
- 우선순위가 빠른 MVP/실사용 검증이다.
- 현재 API는 아바타 CRUD, 버전 관리, 템플릿 조회 중심의 중소 규모다.
- 프론트 변경과 API 변경을 빠르게 동기화해야 한다.
- 팀 규모가 작고 풀스택 개발이 가능한 구성이다.

## 현재 레포 기준 권장안
1. **1단계: Next 내부 백엔드 구현**
- `src/lib/api/types.ts` 계약 유지
- `app/api/*` Route Handlers + DB(Postgres/SQLite) 연결
- `local.ts`는 fallback 또는 dev 모드로 유지

2. **2단계: 경계 준비**
- API 스키마/DTO/에러코드 표준화
- 비즈니스 로직을 서비스 레이어로 분리
- 데이터 모델/마이그레이션 규칙 확정

3. **3단계: 필요 시 Java 분리**
- 동일 계약 기반으로 Java 서비스로 이전
- 프론트는 API client endpoint만 교체해 전환

## 리스크 및 완화
- 리스크: 통합형 백엔드가 비대해져 유지보수 난이도 상승
- 완화: 초반부터 `repository/service/route` 계층 분리, 계약 타입 단일화

- 리스크: 추후 Java 전환 시 재작업
- 완화: 초기에 API 계약(OpenAPI/타입)을 고정하고 호환성 유지

## 최종 판단
현재 프로젝트 성격(아바타 에디터 중심, 빠른 반복 필요, 이미 프론트 API 추상화 존재)을 고려하면,
**단기적으로는 Next 내부 백엔드를 직접 구현하는 것이 비용 대비 효과가 가장 높다.**
다만 공용 플랫폼/API로 확장될 시점에는 Java 분리를 전제로 경계를 준비하는 것이 바람직하다.
