# 액세서리 프리셋 파이프라인 결정사항

이 문서는 현재까지 정리된 액세서리 기능의 설계 결정을 기록한다.

## 1. 최종 방향

이 기능은 사용자에게 실시간으로 새로운 액세서리 GLB를 생성해 주는 기능이 아니다.
대신 Gemini와 VARCO 3D를 사용해 오프라인에서 액세서리 프리셋을 생산하고 검수하는 파이프라인으로 간다.

핵심 흐름은 다음과 같다.

```text
입력 캐릭터 이미지
↓
Gemini로 액세서리 감지
↓
액세서리별 crop / isolation
↓
VARCO 3D로 GLB 후보 생성
↓
파일 기반 검수 및 후처리
↓
approved 프리셋만 라이브러리에 등록
↓
런타임에서는 deterministic mapping으로 적용
```

## 2. 런타임 원칙

- 런타임에서는 새로운 GLB를 생성하지 않는다.
- 런타임은 approved preset만 고른다.
- 장착은 deterministic mapping으로만 처리한다.
- 런타임의 역할은 생성이 아니라 선택, 필터링, 적용이다.

## 3. Gemini의 역할

Gemini는 최종 판단자가 아니라 후보 분석기다.

Gemini가 담당하는 일:

- 액세서리 종류 추정
- 위치와 bbox 후보 추정
- 색상, 크기, 모양 설명
- attach_region 후보 제안
- 분리 난이도 판단
- occlusion risk 판단
- 생성 우선순위 판단

Gemini의 bbox나 mask는 최종 정답이 아니라 crop/isolation 초안으로 본다.

## 4. VARCO 3D의 역할

- VARCO는 runtime 생성기가 아니라 offline asset factory로 사용한다.
- 입력은 캐릭터 전체 이미지가 아니라 액세서리만 분리된 단일 오브젝트 PNG여야 한다.
- VARCO 결과는 후처리와 검수를 거친 뒤에만 라이브러리에 들어간다.

## 5. 전체 Pipeline Stage

파이프라인은 전체 단계로 나눠서 관리한다.

```text
detect
-> crop
-> isolate
-> isolation_validate
-> varco_submit
-> varco_poll
-> download_glb
-> validate_glb
-> postprocess
-> register_preset
```

- `isolation_validate`는 꼭 UI일 필요는 없다.
- 초기에는 파일 저장과 간단한 규칙 검사로 시작한다.
- isolate 결과를 무조건 신뢰하지 않고 검수 가능하게 만드는 것이 목적이다.

## 6. 검수 방식

- human review는 필요하다.
- 다만 MVP에서는 검수 전용 UI를 만들지 않는다.
- 검수는 파일 기반으로 시작한다.
- 검수자는 preview 이미지와 JSON 파일을 보고 `review.json`만 수정하는 방식으로 시작할 수 있다.

### 파일 기반 검수 예시

```text
outputs/accessory_generation/sample_001/
  original.png
  detection.json
  acc_001_crop.png
  acc_001_isolated.png
  acc_001_varco.glb
  acc_001_asset_preview.png
  acc_001_attach_preview.png
  acc_001_review.json
  pipeline_log.json
```

### review.json 예시

```json
{
  "review_status": "pending",
  "quality_score": 0.82,
  "category": "hairpin",
  "attach_region": "head_side_upper",
  "note": "Usable as side hair accessory."
}
```

### 수동 전환 원칙

- 자동 등록은 MVP에서 제외한다.
- `review_status`는 기본적으로 `pending`으로 시작한다.
- 사람이 확인한 뒤에만 `pending -> approved`로 수동 전환한다.
- `approved`가 아닌 프리셋은 런타임 후보에 들어가지 않는다.

## 7. 초기 대상 범위

초기에는 범위를 좁게 시작한다.

### 1차 MVP

- hairpin
- hair_clip
- simple_hair_bow
- glasses

### 1.5차

- headband
- small_crown
- mini_hat

### 후순위

- large_hat
- cap
- complex_hat
- necklace
- earring
- scarf

특히 모자는 초기부터 넓게 다루지 않는다.

## 8. Taxonomy 방향

- taxonomy는 작게 시작한다.
- 처음부터 세분화하지 않는다.
- 우선은 `glasses`, `hairpin`, `hat` 같은 상위 카테고리와 단순 subtype만 둔다.
- 데이터와 검수 경험이 쌓이면 확장한다.

## 9. Metadata 원칙

GLB만 저장하면 안 된다.
프리셋으로 쓰려면 metadata가 핵심이다.

### 필수 필드

- `preset_id`
- `category`
- `asset_path`
- `anchor_bone`
- `attach_region`
- `pivot_policy`
- `default_scale`
- `default_rotation`
- `default_offset`
- `review_status`
- `quality_score`
- `tags`

### 확장 필드

- `source_image_path`
- `crop_image_path`
- `isolated_image_path`
- `varco_request_id`
- `varco_params`
- `face_count`
- `has_texture`
- `bbox`
- `size_hint`
- `symmetry`
- `compatible_avatar_templates`
- `version`
- `created_at`
- `updated_at`

초기에는 필수 + 확장형 구조로 시작하고, 필요할 때만 필드를 늘린다.

## 10. Runtime Mapping 규칙

런타임에서는 생성하지 않고, approved preset만 hard filter 후 scoring한다.

### Hard filter

- `review_status == approved`
- category 일치
- anchor_bone 존재
- GLB 파일 존재
- 현재 아바타 템플릿과 호환

### Scoring

- tag 일치도
- 색상 일치도
- attach_region 일치도
- symmetry 일치도
- quality_score

런타임은 항상 안정적으로 동작해야 하며, 불안정한 생성 로직을 포함하지 않는다.

## 11. 코드 기준 필드명 통일

문서와 코드에서 필드명은 다음 기준으로 통일한다.

- `anchor_bone`: 런타임 장착 기준이 되는 본 이름
- `attach_region`: 얼굴/머리/몸의 부착 영역

이 문서에서는 `anchor_bone`를 기준 필드로 사용하고, `attach_region`는 보조 분류 정보로 유지한다.

## 12. 헤어 코드에서 가져온 원칙

현재 코드베이스의 헤어 기능은 이미 같은 철학을 따른다.

- 이미지 분석
- 프리셋 추천
- 메타데이터 기반 매칭
- 런타임 deterministic attachment

액세서리도 이 패턴을 따라가되, 헤어의 `meshCount` 같은 지표는 그대로 복붙하지 않는다.
액세서리에서는 `shape`, `symmetry`, `bbox`, `attach_region`, `size_hint`가 더 중요하다.

## 13. 현재 확정된 한 줄 요약

이 기능은 Gemini와 VARCO를 이용해 액세서리 프리셋을 빠르게 생산하는 오프라인 파이프라인으로 설계하고, 사용자에게는 검수된 프리셋만 간단히 선택·적용할 수 있는 UI를 제공하는 방향으로 간다.

## 14. 아직 미정인 항목

- 정확한 scoring 규칙
- 카테고리별 anchor bone 매핑
- 자동 등록의 정량 기준
- 검수 UI의 최종 범위
- 라이브러리 저장 포맷을 TS, JSON, DB 중 무엇으로 둘지
