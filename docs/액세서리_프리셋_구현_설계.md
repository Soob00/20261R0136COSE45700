# 액세서리 프리셋 구현 설계

이 문서는 [액세서리_프리셋_파이프라인_결정사항.md](C:\Users\yscho\projects\Practice_SW\20261R0136COSE45700\docs\액세서리_프리셋_파이프라인_결정사항.md)를 구현으로 옮기기 위한 설계를 정리한다.

## 1. 설계 목표

이 설계의 목표는 다음 네 가지다.

- 오프라인 프리셋 생산 파이프라인과 런타임 적용 경로를 명확히 분리한다.
- 현재 헤어/의상 구조와 충돌하지 않도록 액세서리 기능을 확장한다.
- MVP에서는 review UI와 자동 등록 없이도 파이프라인이 돌아가게 만든다.
- 나중에 taxonomy, scoring, 저장소를 확장하더라도 타입과 모듈 경계가 흔들리지 않게 한다.

## 2. 비목표

MVP에서 하지 않는 일:

- 런타임 GLB 생성
- review UI
- `pending -> approved` 자동 승격
- 고급 postprocess
- 복수 아바타 템플릿 자동 보정

## 3. 핵심 아키텍처

기능은 두 흐름으로 나뉜다.

### 3.1 Offline 프리셋 생산

```text
입력 이미지
-> Gemini detect
-> crop
-> isolate
-> isolation_validate
-> varco_submit
-> varco_poll
-> download_glb
-> validate_glb
-> postprocess
-> review
-> review.json 생성 (pending)
-> 사람이 approved로 수동 전환
-> register_preset
```

### 3.2 Runtime 추천 및 적용

```text
입력 이미지 또는 현재 캐릭터 문맥
-> Gemini detect
-> approved preset hard filter
-> deterministic scoring
-> 슬롯별 추천 결과 생성
-> 사용자 적용 / 해제
-> GLB attachment
```

런타임은 프리셋을 고르는 곳이고, 오프라인은 프리셋을 만드는 곳이다.

## 4. 가장 중요한 구조적 결정

### 4.1 액세서리는 단일 값이 아니라 슬롯 집합으로 관리한다

헤어는 `hairFrontUrl`, `hairBackUrl`처럼 단일 조합으로 다루지만, 액세서리는 최소한 다음을 동시에 가질 수 있다.

- 안경
- 좌측 헤어핀
- 우측 헤어핀
- 머리 위 장식

따라서 액세서리를 `accessoryUrl: string | null` 같은 단일 필드로 두면 설계가 바로 막힌다.
MVP부터 슬롯 기반 구조로 가는 것이 맞다.

MVP store 형태는 아래처럼 잡는다.

```ts
accessories: Partial<Record<AccessorySlot, AppliedAccessory | null>>;
```

장기적으로 같은 슬롯에 복수 액세서리를 허용할 수 있지만, MVP에서는 충돌 규칙과 UI 복잡도를 줄이기 위해 슬롯당 1개만 허용한다.

### 4.1.1 적용 상태와 추천 상태의 수명을 분리한다

현재 store는 실제 편집 상태를 중심으로 undo/redo, version 저장, reset을 수행한다.
액세서리도 같은 규칙을 따라야 하지만, 추천 결과까지 같은 수명으로 다루면 안 된다.

- `accessories`: 실제 편집 상태, undo/redo 및 version 저장 대상
- `accessoryRecommendations`: 임시 계산 결과, undo/redo 및 version 저장 비대상

이 원칙이 없으면 추천 재계산이 편집 이력에 섞이고, 사용자가 직접 적용한 액세서리와 추천 결과가 충돌한다.

### 4.2 런타임 기준은 `anchor_bone`, 탐지 기준은 `attach_region`

- `attach_region`: Gemini가 제안하는 부착 영역
- `anchor_bone`: 실제 3D attachment가 참조하는 본 이름

이 둘을 분리해야 한다.
Gemini는 장면 의미를 알고, 런타임은 본 구조를 안다.

추가 규칙:

- `attachRegion`은 detect 및 scoring 입력으로 사용한다.
- `anchorBone`는 최종 attachment 시 사용한다.
- `anchorBone`는 preset 값이 우선이고, 비어 있거나 무효하면 `slot -> default bone` fallback을 사용한다.

MVP 기본 fallback은 모두 `Head`로 시작한다.
bone 탐색 실패 시 다른 bone을 추론하지 않고 attach를 실패로 처리하는 것이 안전하다.

### 4.3 액세서리는 rigid GLB로 시작한다

MVP에서는 spring bone, cloth, secondary animation을 넣지 않는다.
초기 범위가 `glasses`, `hairpin`, `hair_clip`, `hair_bow`이므로 rigid attachment만으로 충분하다.

## 5. 제안 타입 설계

### 5.1 taxonomy v0

```ts
export type AccessoryCategory =
  | 'glasses'
  | 'hairpin'
  | 'hair_clip'
  | 'hair_bow';
```

머리 위 장식 계열은 MVP taxonomy에서 일반 `hat`으로 열지 않는다.
필요하면 1.5차에서 아래처럼 확장한다.

```ts
export type HeadAccessorySubtype =
  | 'headband'
  | 'small_crown'
  | 'mini_hat';
```

### 5.2 부착 슬롯

런타임은 의미 기반 슬롯으로 관리한다.

```ts
export type AccessorySlot =
  | 'face_center'
  | 'head_side_left'
  | 'head_side_right'
  | 'head_top';
```

이 슬롯은 UI와 store의 기준이다.

슬롯 규칙:

- MVP에서는 슬롯당 1개만 허용한다.
- 같은 슬롯에 새 액세서리를 적용하면 기존 액세서리를 대체한다.
- 추천 결과는 슬롯별로 계산하되 자동 적용하지 않는다.
- 추천 재계산이 발생해도 이미 적용된 액세서리를 자동 교체하지 않는다.

### 5.3 attach region

탐지 결과는 더 느슨한 의미 영역을 가진다.

```ts
export type AttachRegion =
  | 'face_center'
  | 'head_side_upper_left'
  | 'head_side_upper_right'
  | 'head_top';
```

MVP에서는 `AttachRegion -> AccessorySlot` 매핑 테이블을 별도로 둔다.

### 5.4 review status

```ts
export type ReviewStatus = 'pending' | 'approved' | 'rejected';
```

### 5.5 pipeline stage

export type AccessoryPipelineStage =

export type FailureReason =

```ts
export interface AccessoryPreset {
  presetId: string;
  name: string;
  category: AccessoryCategory;
  slot: AccessorySlot;
  assetPath: string;
  thumbnailPath: string;
  anchorBone: string;
  attachRegion: AttachRegion;
  pivotPolicy: 'object_center' | 'contact_point_back_center';
  defaultScale: number;
  defaultRotation: [number, number, number];
  defaultOffset: [number, number, number];
  reviewStatus: ReviewStatus;
  qualityScore: number;
  tags: string[];
  dominantColorHex: string | null;
  paletteHexes: string[];
  symmetry: 'single' | 'paired';
  compatibleAvatarTemplates?: string[];
  sourceImagePath?: string;
  cropImagePath?: string;
  isolatedImagePath?: string;
  varcoRequestId?: string;
  varcoParams?: Record<string, unknown>;
  faceCount?: number;
  hasTexture?: boolean;
  bbox?: [number, number, number, number];
  sizeHint?: 'small' | 'medium' | 'large';
  version: number;
  createdAt: string;
  updatedAt: string;
}
```

오프라인 JSON DTO는 별도로 둔다.

```ts
export interface AccessoryPresetFile {
  preset_id: string;
  name: string;
  category: AccessoryCategory;
  slot: AccessorySlot;
  asset_path: string;
  thumbnail_path: string;
  anchor_bone: string;
  attach_region: AttachRegion;
  pivot_policy: 'object_center' | 'contact_point_back_center';
  default_scale: number;
  default_rotation: [number, number, number];
  default_offset: [number, number, number];
  review_status: ReviewStatus;
  quality_score: number;
  tags: string[];
  dominant_color_hex: string | null;
  palette_hexes: string[];
  symmetry: 'single' | 'paired';
  compatible_avatar_templates?: string[];
  source_image_path?: string;
  crop_image_path?: string;
  isolated_image_path?: string;
  varco_request_id?: string;
  varco_params?: Record<string, unknown>;
  face_count?: number;
  has_texture?: boolean;
  bbox?: [number, number, number, number];
  size_hint?: 'small' | 'medium' | 'large';
  version: number;
  created_at: string;
  updated_at: string;
}
```

런타임은 항상 `AccessoryPresetFile -> AccessoryPreset` adapter를 거친다.

추가 규칙:

- `AccessoryPresetFile`은 오프라인 JSON source of truth용 DTO다.
- `AccessoryPreset`은 런타임 UI와 attachment가 사용하는 정규화된 타입이다.
- adapter 단계에서 `approved` 필터링, camelCase 변환, 기본값 보정, enum 검증을 수행한다.
- preset 색상 메타데이터는 `dominantColorHex`와 `paletteHexes`로 고정한다.
- `dominantColorHex`는 대표색 1개, `paletteHexes`는 scoring용 비교 팔레트다.

### 5.8 런타임 적용 상태

store에는 프리셋 전체가 아니라 적용 상태를 저장한다.

```ts
export interface AppliedAccessory {
  presetId: string;
  slot: AccessorySlot;
  colorOverride?: string | null;
}
```

권장 store 확장:

```ts
accessories: Partial<Record<AccessorySlot, AppliedAccessory | null>>;
accessoryRecommendations: Partial<Record<AccessorySlot, AccessoryPreset[]>>;
```

여기서 `accessories`만 snapshot 및 version 저장 대상이다.

### 5.9 탐지 결과

```ts
export interface DetectedAccessoryCandidate {
  id: string;
  category: AccessoryCategory | 'unknown' | 'unsupported';
  bbox: [number, number, number, number];
  attachRegion: AttachRegion;
  confidence: number;
  rawColors: string[];
  normalizedColors: string[];
  sizeHint?: 'small' | 'medium' | 'large';
  occlusionRisk: 'low' | 'medium' | 'high';
  isolationDifficulty: 'low' | 'medium' | 'high';
  generationPriority: 'low' | 'medium' | 'high';
  shapeDescription: string;
}
```

detect 결과는 `unknown` 또는 `unsupported`를 가질 수 있어야 한다.
반면 등록된 preset metadata의 `category`는 반드시 `AccessoryCategory`만 허용한다.

정규화 규칙:

- Gemini raw 색상은 자유 텍스트 또는 색상명을 허용한다.
- 정규화 단계에서 palette mapper가 raw 색상을 hex 문자열 목록으로 변환한다.
- scoring에는 `normalizedColors`만 사용한다.
- 정규화 실패 시 빈 배열을 허용하고, 색상 정보는 hard filter에 사용하지 않는다.
- `shapeDescription`은 자유 텍스트로 두되 scoring에는 직접 사용하지 않는다.
- `sizeHint`, `occlusionRisk`, `isolationDifficulty`, `generationPriority`는 enum 값만 허용한다.

## 6. 파일/모듈 배치 설계

현재 코드 구조를 기준으로 다음 배치를 권장한다.

### 6.1 타입

```text

```

포함 내용:

- taxonomy v0
- slot / region / status / stage / failure enum
- `AccessoryPreset`
- `AppliedAccessory`
- `DetectedAccessoryCandidate`

색상 정규화 유틸:

```text
src/lib/accessory-matching/color-normalizer.ts
```

역할:

- Gemini raw 색상명 또는 raw hex를 정규화한다.
- preset `dominantColorHex`, `paletteHexes`를 같은 hex 포맷으로 정규화한다.
- scoring 입력이 항상 동일한 palette space를 보도록 강제한다.

### 6.2 정적 데이터

```text
data/accessory-presets.json

```

역할:

- `accessory-presets.json`을 source of truth로 사용

추가 원칙:

- `accessory-presets.ts`는 단순 재수출이 아니라 validate + normalize 계층으로 둔다.
- 새 패키지는 추가하지 않고, MVP에서는 수동 validator 함수로 시작한다.
- JSON 원본의 수동 수정은 허용하지 않는다.
- `register-accessory-preset.py`만 JSON 원본을 갱신한다.

### 6.3 런타임 매칭 로직

## 7. 기존 코드에 대한 구체적 확장 포인트

### 7.1 `src/types/preset.ts`

현재 `PresetCategory`는 `hair | outfit | accessory`까지만 있다.
여기에는 UI 범주만 유지하고, 실제 액세서리 taxonomy는 `src/types/accessory.ts`로 분리한다.

이유:

- `PresetCategory`는 화면 분류
- `AccessoryCategory`는 파이프라인/런타임 분류

두 역할이 다르기 때문이다.

추가 규칙:

- `PresetCategory`는 기존 UI 탭 분류를 유지한다.
- `AccessoryPanel`은 `AccessoryPreset`을 전용 카드 모델로 렌더링한다.
- 기존 `PresetGrid.tsx`를 억지로 범용화하지 않는다.

### 7.2 `src/types/editor.ts`

현재는 `hairFrontUrl`, `hairBackUrl`, `outfitUrl`만 있다.
여기에 액세서리를 단일 필드로 추가하지 말고 슬롯 기반 상태를 추가한다.

권장 추가:

```ts
accessories: Partial<Record<AccessorySlot, AppliedAccessory | null>>;
accessoryRecommendations: Partial<Record<AccessorySlot, AccessoryPreset[]>>;
```

상태 수명 규칙:

- `accessories`는 실제 편집 상태다.
- `accessoryRecommendations`는 세션성 계산 결과다.
- `accessoryRecommendations`는 version 저장, restore, reset 복구 대상이 아니다.

### 7.3 `src/stores/editorStore.ts`

권장 액션:

- `setAccessory(slot, applied)`
- `removeAccessory(slot)`
- `setAccessoryRecommendations(slot, presets)`
- `clearAccessoryRecommendations()`

헤어와 달리 액세서리는 복수 동시 장착이 가능하므로 `setAccessoryUrl` 같은 단일 API는 피한다.

추가 필수 변경:

- `snapshot()`에 `accessories`를 포함한다.
- undo/redo에 `accessories`를 포함한다.
- `saveVersion()`과 `restoreVersion()`에 `accessories`를 포함한다.
- `resetAll()`은 `accessories`를 초기화한다.
- `accessoryRecommendations`는 snapshot에 넣지 않고, reset 시 비우기만 한다.

즉, 추천 결과는 편집 히스토리의 일부가 아니고, 적용 상태만 히스토리의 일부다.

### 7.4 `src/components/viewer/ThreeJSViewer.tsx`

`HairAttachment`, `OutfitAttachment`와 동일한 위치에 `AccessoryAttachment`를 추가한다.

```tsx
<VRMModel ... />
<HairAttachment />
<OutfitAttachment />
<AccessoryAttachment />
```

### 7.5 `src/components/editor/ReferenceModelUpload.tsx`

현재 이 컴포넌트는 헤어 추천, 텍스처, face-keys를 병렬로 처리한다.
액세서리까지 넣으려면 책임이 너무 커진다.

MVP에서는 다음 둘 중 하나가 적절하다.

- 별도 `AccessoryReferenceUpload.tsx` 추가
- `ReferenceModelUpload.tsx` 내부에서 accessory 로직만 별도 훅으로 분리

권장 방향은 별도 훅이다.

```text
src/hooks/useAccessoryRecommendation.ts
```

이 훅은 runtime 추천만 담당하고, 오프라인 생성은 담당하지 않는다.

추가 규칙:

- 훅은 detect 결과 정규화와 matcher 호출까지만 담당한다.
- store의 `setAccessoryRecommendations()` 호출은 상위 컨테이너 또는 패널에서 수행한다.
- runtime 훅에서 offline pipeline script를 호출하지 않는다.

## 8. 오프라인 산출물 설계

샘플 단위 디렉터리:

```text
outputs/accessory_generation/sample_001/
  original.png
  detection.json
  pipeline_log.json
  crops/
    acc_001_crop.png
  isolated/
    acc_001_isolated.png
  varco/
    acc_001_submit.json
    acc_001_result.json
  glb_raw/
    acc_001_raw.glb
  preview/
    acc_001_asset_preview.png
    acc_001_attach_preview.png
  review/
    acc_001_review.json
```

이 구조를 고정하면 review UI 없이도 검수가 가능하다.

추가 원칙:

- `pipeline_log.json`은 stage append-only 로그로 둔다.
- 마지막 stage만 저장하지 말고, 각 stage의 시작/성공/실패를 모두 남긴다.
- 실패 재현을 위해 입력 파일 경로와 주요 파라미터를 같이 기록한다.
- 검수자가 수동 수정할 수 있는 파일은 `review/*.json`으로 제한한다.
- `detection.json`, `pipeline_log.json`, `varco/*.json`은 원본 로그로 간주하고 수동 수정하지 않는다.

## 9. register_preset 설계

등록은 별도 스크립트로 분리한다.

입력:

- `review_status == approved`
- GLB 경로 존재
- preview 존재
- 메타데이터 필수 필드 존재

출력:

- `public/models/accessory-library/{preset_id}.glb`
- `public/thumbnails/accessory/{preset_id}.png`
- `data/accessory-presets.json`에 등록용 entry 추가
- `src/data/accessory-presets.ts`는 JSON import 결과를 검증해서 노출

MVP에서는 DB 대신 파일 기반 등록이 적절하다.

등록 규칙:

- register는 atomic하게 동작해야 한다.
- asset copy 실패 시 JSON은 갱신하지 않는다.
- JSON 갱신 실패 시 partially copied asset을 정리하거나 retry 대상으로 남긴다.
- `approved`가 아니면 register를 즉시 실패시킨다.
- 동일한 `presetId`가 이미 존재하면 MVP에서는 overwrite하지 않고 실패시킨다.
- preset 수정은 새 `presetId`를 발급하거나 `version`을 증가시키는 별도 절차로 처리한다.

## 10. Runtime scoring 설계

런타임 scoring은 설명 가능한 규칙이어야 한다.
초기 권장 가중치는 다음과 같다.

```text
category match: hard filter
slot compatibility: hard filter
attach_region match: 0.30
tag overlap: 0.25
color similarity: 0.20
symmetry match: 0.10
quality_score: 0.15
```

MVP에서는 이 정도의 고정 가중치로 충분하다.
학습 기반 추천은 이후 단계로 미룬다.

fallback 규칙:

- hard filter 결과가 비면 아무 것도 적용하지 않는다.
- 점수 차이가 작더라도 deterministic하게 하나만 선택한다.
- 동점이면 `qualityScore`가 높은 것을 우선하고, 그래도 같으면 `presetId` 사전순으로 고정한다.

입력 정규화 규칙:

- preset `tags`는 소문자 slug 배열로 통일한다.
- detect 단계의 `rawColors`는 자유 텍스트를 허용하고, palette mapper를 거쳐 `normalizedColors`로 변환한다.
- preset 색상 정보는 `dominantColorHex`와 `paletteHexes`를 사용하고, 같은 palette space의 hex 포맷으로 정규화한 뒤 비교한다.
- `color similarity`는 raw 문자열이 아니라 정규화된 hex 기준으로만 계산한다.
- `sizeHint`는 scoring 보조 정보로만 사용하고 hard filter에는 넣지 않는다.
- `symmetry`는 preset 정의를 기준으로만 사용한다.

## 11. 최소 postprocess 범위

MVP에서 postprocess는 최소화하되 제거하지 않는다.

필수:

- 기본 GLB 로딩 검사
- face count 기록
- bounds 또는 대략적인 크기 기록
- default scale 정리
- default rotation 정리
- default offset 정리
- pivot_policy 기록
- preview render 생성
- base avatar attach preview 생성

제외:

- 고급 decimation
- 재질 재구성
- 자동 collision tuning
- 고급 텍스처 수정
- 자동 pivot 보정

## 12. 구현 순서

좋은 구현 순서는 다음과 같다.

1. `src/types/accessory.ts` 정의
2. enum, review, failure log 타입 고정
3. `data/accessory-presets.json` 및 `src/data/accessory-presets.ts` 초기 골격 추가
4. 테스트용 approved dummy preset 준비
5. store 확장
6. `AccessoryAttachment.tsx` 추가
7. `AccessoryPanel.tsx` 추가
8. runtime matcher 추가
9. 파일 기반 offline pipeline script 추가
10. register script 추가
11. `ReferenceModelUpload`와 accessory 추천 연결

이 순서가 좋은 이유는 런타임 구조를 먼저 세우고, 오프라인 파이프라인은 그 구조에 맞춰 붙일 수 있기 때문이다.

런타임 구조를 먼저 검증하려면 최소 1개 이상의 approved dummy preset이 반드시 필요하다.

권장 더미 자산:

- `dummy_glasses_001`
- 대응 thumbnail 1개
- JSON entry 1개

더미 자산 요구사항:

- 실제 `approved` preset과 동일한 필드 집합을 가진다.
- `AccessoryAttachment`와 `AccessoryPanel`을 end-to-end로 검증할 수 있어야 한다.
- slot, anchorBone, default transform, thumbnail, GLB 경로가 모두 유효해야 한다.

## 13. 구현 시 주의사항

- 액세서리를 단일 URL 필드로 만들지 않는다.
- `approved`가 아닌 프리셋은 절대 런타임 후보에 넣지 않는다.
- `anchor_bone`와 `attach_region`를 혼동하지 않는다.
- `ReferenceModelUpload.tsx`에 모든 책임을 몰아넣지 않는다.
- MVP에서 review UI를 만들려 하지 않는다.
- 파이프라인과 런타임 매칭 규칙은 같은 taxonomy를 공유해야 한다.
- detect 결과와 preset 등록 카테고리의 허용 범위를 같게 만들지 않는다.
- `hat` 같은 넓은 분류를 MVP taxonomy에 바로 넣지 않는다.
- 오프라인 JSON을 곧바로 UI 타입으로 쓰지 않는다.
- register script가 TypeScript 소스 파일을 직접 수정하게 만들지 않는다.
- 추천 결과를 자동 적용 상태와 같은 수명으로 다루지 않는다.
- clone attachment와 cache 원본의 dispose 책임을 혼동하지 않는다.

## 14. 최종 설계 요약

좋은 설계의 핵심은 다음이다.

- 파이프라인과 런타임을 분리한다.
- 액세서리를 슬롯 기반 상태로 관리한다.
- rigid attachment만 먼저 지원한다.
- 파일 기반 검수와 수동 승인만 허용한다.
- approved preset만 deterministic하게 적용한다.
